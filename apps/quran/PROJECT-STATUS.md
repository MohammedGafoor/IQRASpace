## 2. Existing technology (relevant to this build)

Found in `apps/web`, useful as *reference/reuse candidates*, not as a shared runtime:

- **Stack pattern:** Next.js 16 (App Router) + React 19 + TypeScript + Tailwind CSS v4 + ESLint flat config + `tsc --noEmit`. Node `>=20.9.0` (dev machine has 24.19.0). No test framework configured yet anywhere in the repo.
- **Design tokens:** `apps/web/src/app/globals.css` has a working Islamic-inspired token set (warm ivory paper, emerald/teal + gold accents, Fraunces/Inter/Amiri via `next/font/google`, class-based dark mode) and a `components/ui/` primitives library. Same visual *language* the master prompt asks for (§12), but built for a dashboard app, not a reading experience — treat as a style reference, not a package to import.
- **Quran text:** `apps/web/src/lib/quranContent.ts` bundles 5 short surahs (Al-Fatiha, Al-Ikhlas, Al-Falaq, An-Nas, Al-Asr) as hardcoded Uthmani-script constants, used only for that app's live highlight-sync teaching feature. **Not usable as this product's content source** — it's a tiny hardcoded sample with no translation, audio, or metadata layer, and the master prompt explicitly forbids hand-typing Quran text (§7). A real content provider is still required from scratch.
- **PDF/RTL handling:** `components/pdf/PdfViewer.tsx` proves out pdf.js + Arabic/RTL text layers + JBIG2/WASM asset wiring in this repo's environment already — useful precedent if any PDF-based content (e.g. Mushaf page images) is ever considered, not a dependency for Phase 1.
- **CI/CD pattern:** `.github/workflows/ci.yml` — single workflow, `working-directory: apps/web` hardcoded, `validate` (lint/typecheck/build) → `deploy` (Vercel CLI, prebuilt, prod) → health check against a fixed pilot alias. This workflow **will run its `validate` job on every push regardless of which app changed** — it has no path filter today.
- **Supabase project:** one hosted project (ref `pqlrexhtwgleokyiamie`) already serves `apps/web`, on the free tier, with RLS policies scoped to the tutoring domain (tutors/students/classes/lessons/admin roles).
- **Vercel project:** one project (`shaga2/iqraspace`) already serves `apps/web`; Deployment Protection (SSO) is on for the team, only the stable alias is public.

## 5. Risks and open decisions

These need a deliberate answer before Phase 0 scaffolding starts (a recommendation is given for each in [`ARCHITECTURE.md`](./ARCHITECTURE.md), but flagging them here as things to confirm, not silently assume):

1. **Infra isolation.** Should this product get its **own Supabase project** and **own Vercel project**, or share the existing ones? Recommendation: separate, for both — different privacy/auth model (anonymous-first public app vs. minors'-data tutoring app behind auth), different blast radius, different RLS posture, and no cost penalty (both are $0 at this scale). *Needs verifying: current Supabase free-tier project-count limit per org* — the source architecture doc for the existing app already flags free-tier limits as something that "changes fairly often" and must be re-checked at build time, not assumed from training data.
2. **CI/CD split.** The existing workflow has no path filtering and hardcodes `apps/web`. Adding `apps/quran` needs either a second workflow file or path-filtered jobs in the same file, so a change to one app never gates or redeploys the other, and a break in one app's `validate` job never blocks the other's pipeline.
3. ~~**Domain/branding.**~~ — decided: `iqraspace.org/quran`, via a Next.js Multi-Zones path rewrite once the Vercel project exists (`ARCHITECTURE.md` §8). `next.config.ts` is already prepared for this (`NEXT_BASE_PATH` env var, unset today). What serves `iqraspace.org`'s own root is still undecided — not this app's concern, tracked as open.
4. **Content provider — researched and resolved.** ~~Its current auth model, rate limits, and commercial/non-commercial licensing terms have not been checked yet~~ — done, see [`QURAN-CONTENT.md`](./QURAN-CONTENT.md). Quran Foundation's Content APIs (v4.0.0) are confirmed usable for a free, non-commercial app under OAuth2 client-credentials auth. One finding changed the architecture: cached content must be re-synced **at least every 7 days** (a license term, not a preference) — `ARCHITECTURE.md` §4 has been corrected accordingly. Two things remain genuinely open: (a) exact numeric rate limits are unpublished until a project is registered, and (b) a full-text **Search** endpoint was not confirmed to exist — verify directly before Phase 3 is architected. Registering a developer account/project is an action only the project owner can take (see §6 below and `QURAN-CONTENT.md` §5) — this session cannot create third-party accounts.
5. **Monorepo tooling stays minimal.** No workspaces/Turborepo exist today and none are proposed — `apps/quran` will be a fully independent Next.js app with its own `package.json`, mirroring how `apps/web` is already structured, orchestrated only via root `package.json` `--prefix` scripts. Revisit only if real duplication pain shows up later (KISS, per master prompt §41).
